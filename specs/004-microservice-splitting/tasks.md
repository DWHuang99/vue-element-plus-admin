## Dependencies & Execution Order

### Phase Dependencies

- **Setup (Phase 1)**: No dependencies - can start immediately
- **Foundational (Phase 2)**: Depends on Setup completion - BLOCKS all user stories
- **User Stories (Phase 3+)**: All depend on Foundational phase completion
  - User stories can then proceed in parallel (if staffed)
  - Or sequentially in priority order (P1 → P2 → P3)
- **Polish (Final Phase)**: Depends on all desired user stories being complete

### User Story Dependencies

- **User Story 1 (P1)**: 依赖 Foundational（T005–T016）。auth/RBAC 读链路独立可测；`/auth/me` 与用户列表组成（T028/T029/T030）消费 Organization ports（T007 骨架定义），department 字段全绿需 US2 membership 实现（T035/T036），在 T031 Checkpoint 处集成。
- **User Story 2 (P1)**: 依赖 Foundational。与 US1 可并行开发；T040 inbox consumer 是 US4 dispatcher 的调用目标（US4 依赖）。
- **User Story 3 (P2)**: 依赖 US1（IAM 模块与 BFF transport 就绪）+ US2（membership ports）。delete workflow（T054）写入 outbox 行，是 US4 的生产端。
- **User Story 4 (P2)**: 依赖 US2（T040 Organization inbox consumer）+ US3（T048/T054 IAM delete + outbox 生产端）。
- **User Story 5 (P3)**: 依赖 US1–US4 全部（readiness/observability 覆盖所有模块；rollout 演练以完整能力为前提）。

### Within Each User Story

- 契约测试先行并先行跑红（T017/T018/T033/T043/T050/T061）→ 实现 → 故障注入矩阵作为 story gate（T059/T067/T079/T080）
- Models → Services → Adapters → BFF transport → Integration
- Story complete before moving to next priority

### Parallel Opportunities

- All Setup tasks marked [P] can run in parallel
- All Foundational tasks marked [P] can run in parallel（T006/T007/T008 骨架；迁移与测试任务按 owner 分工）
- Once Foundational phase completes, US1 and US2 can start in parallel (if team capacity allows)
- US3 and US4 can run in parallel once US1/US2 的依赖任务完成
- Different user stories can be worked on in parallel by different team members

## Implementation Strategy

### MVP First (User Story 1 Only)

1. Complete Phase 1: Setup（baseline 冻结与证据）
2. Complete Phase 2: Foundational（契约套件、骨架、迁移、sqlc 拆分——CRITICAL，阻塞全部 story）
3. Complete Phase 3: User Story 1（行为兼容边界 + BFF 读路径）
4. **STOP and VALIDATE**: T017/T018 契约与 T031 Checkpoint 独立验证 US1
5. Deploy/demo if ready

### Incremental Delivery

1. Complete Setup + Foundational → Foundation ready
2. Add User Story 1 → 独立验证 → Deploy/Demo（MVP）
3. Add User Story 2（Organization 抽取就绪）→ 独立验证
4. Add User Story 3（写工作流一致性）→ 独立验证（Checkpoint E）
5. Add User Story 4（outbox/inbox 闭环）→ 独立验证（Checkpoint F）
6. Add User Story 5（可观测 + 分阶段发布）→ 演练验证
7. Polish：legacy 清理 + 最终质量门禁

### Parallel Team Strategy

With multiple developers:

1. Team completes Setup + Foundational together
2. Once Foundational is done:
   - Developer A: User Story 1（IAM 迁移 + BFF transport）
   - Developer B: User Story 2（Organization 模块）
3. After US1+US2 dependencies land:
   - Developer A: User Story 3（写工作流）
   - Developer B: User Story 4（outbox/inbox）
4. Developer C: User Story 5（可观测与发布）
5. Stories complete and integrate independently

## Notes

- [P] tasks = different files, no dependencies
- [Story] label maps task to specific user story for traceability
- Each user story should be independently completable and testable
- 契约测试先行：验证测试先红再实现
- 密码/原始 token/hash/DB secret 永不进入 workflow/receipt/event/log（每个 story 的隐私断言）
- sqlc 生成文件只由 `sqlc generate` 更新
- 不重写迁移 000001–000005；000004/000005 不在本 feature 回滚
- 不引入 gRPC runtime/broker/Redis/服务发现/独立进程
- Commit after each task or logical group（用户未要求时不要 push）
- 当前工作树有大量未提交改动：不要 reset/checkout/覆盖他人工作
- Stop at any checkpoint to validate story independently
